## يبقى العملاء متصلين بعد انتهاء باقتهم

مهمة cron لا تعمل. تنتهي الباقات وتتجدد عبر `system/cron.php`، فلا شيء ينتهي بدونها.

1. افتح لوحة التحكم. يعرض ودجت cron وقت آخر تشغيل للمهمة، وينبّهك بعد 24 ساعة.
2. شغّل المهمة يدويًا من مجلد `system` واقرأ المخرجات:

   ```bash
   cd /path/to/site/system && php cron.php
   ```

3. إذا نجح ذلك ولم تعمل الجدولة، فافحص سطر crontab من صفحة [التثبيت](/ar/docs/getting-started/installation/#cron). السبب المعتاد مسار PHP خاطئ. اعرف مسارك بالأمر `which php`.
4. إذا لم تستطع جدولة مهام CLI (بعض الاستضافات المشتركة)، فيمكن أيضًا طلب `cron.php` عبر HTTP من مجدوِل خارجي.

## صفحة بيضاء أو خطأ 500

1. تأكد أن PHP بإصدار 8.2 أو أحدث وأن امتدادات PDO وMySQLi وGD وcURL وZIP وmbstring محمّلة.
2. اقرأ سجل أخطاء خادم الويب. فهو يذكر الملف والسطر.
3. لعرض الأخطاء في المتصفح على جهاز اختبار، اضبط `$_app_stage` في `config.php` على أي قيمة غير `Live`. أعدها بعد ذلك، لأنها تعرض الأخطاء لعملائك أيضًا.
4. تُعرض الأخطاء غير المعالجة في صفحة خطأ، فالصفحة شبه الفارغة تعني غالبًا أن خطأً وقع، لا أن شيئًا لم يحدث.

## كل الصفحات تعطي 404 ما عدا الصفحة الرئيسية

الروابط الجميلة تحتاج إلى إعادة كتابة (rewrite).

- **Apache:** فعّل `mod_rewrite` واضبط `AllowOverride All` للموقع، ليُقرأ ملف `.htaccess` في الجذر.
- **Nginx:** وجّه كل مسار ليس ملفًا إلى `index.php?_route=$1`.

للتأكد أن هذه هي المشكلة، افتح `index.php?_route=login`. إذا عمل فالسبب هو إعادة الكتابة.

## "Permission denied" أو إعدادات لا تُحفظ

يجب أن يستطيع خادم الويب الكتابة في `system/uploads/` و`system/cache/` و`ui/compiled/` و`ui/cache/` و`system/lan/`.

```bash
sudo chown -R www-data:www-data /var/www/html
```

المستخدم هو `www-data` في Debian وUbuntu. وفي أنظمة أخرى قد يكون `apache` أو `nginx`.

## الصفحات تبدو قديمة بعد التحديث

القوالب تُترجَم وتُخزَّن مؤقتًا. احذف الملفات داخل `ui/compiled/` و`ui/cache/` (أبقِ المجلدات)، ثم أعد التحميل. حدّث المتصفح أيضًا بتحديث إجباري ليتخلص من ورقة الأنماط المخزنة.

## الراوتر لا يتصل

راجع [ربط راوتر](/ar/docs/getting-started/connect-a-router/). تأكد أن خدمة API مفعّلة على الراوتر، وأن لا قاعدة جدار ناري تحجب منفذ API عن الخادم، وأن مستخدم الراوتر يستطيع استخدام API.

## دفع العميل لكن الباقة لم تنشط

لم تستطع البوابة الوصول إلى PHPNuxBill، أو لم يستطع PHPNuxBill تأكيد الدفع.

1. افحص عنوان callback الذي أعطيته للبوابة. راجع [بوابات الدفع](/ar/docs/using/payment-gateways/#عنوان-callback).
2. تأكد أن الموقع على عنوان عام مع HTTPS. لا تستطيع البوابة استدعاء `localhost` ولا عنوان IP خاصًا.
3. افتح تدقيق بوابة الدفع (payment gateway audit) في لوحة الإدارة وانظر في المعاملة وفي رد البوابة.

## ما زلت عالقًا؟

راجع [الحصول على المساعدة](/ar/docs/getting-started/getting-help/). اذكر الإصدار الذي تستخدمه وما كنت تتوقعه وما حدث وأي نص خطأ.
